Abstract

Interactive video world models let a user explore a generated world in real time, from games to simulators for embodied agents. Current models with the best quality are too large for the user’s device. They run in the cloud, where each user occupies a GPU and every action waits for the network. A small model fits on the device and responds immediately, but it loses details and drifts over time. We study the largely unexplored edge–cloud setting, in which a large cloud model and a small model on the edge device collaborate on generating one video. The video quality that the user sees trades off against the cloud cost of producing it. More computation in the cloud improves the video, but it costs more and slows it down. We present HIVE, a heterogeneous collaboration framework in which the cloud keeps only the work that needs the large model. The edge device does the rest and handles new actions itself. HIVE delivers video quality close to that of the large cloud model. It runs 2.9× faster than cloud-only generation and uses 2.9× less cloud GPU energy, and it responds to a new action as fast as the on-device model.

Method

How HIVE splits the work

While the action persists, one denoising step of the large model is enough: in a few-step distilled world model its first clean estimate is already a usable chunk. Where the action changes, the small model is enough, because the history it continues from was made by the large model.

One-step lookahead

While chunk i−1 is on screen, the cloud predicts chunk i under the current action and returns only its first clean estimate. One denoising pass replaces four, the network latency hides behind the chunk being displayed, and the cloud never runs the VAE decoder.

Device · 1.3B

Decoding and regeneration

The device decodes the cloud estimates. When the user changes the action, the prediction made under the old action is discarded and the device regenerates that chunk with its full four-step sampler, on the machine that receives the action first and without the network.

Both

Shared history

Every displayed chunk, whichever model made it, enters the KV cache of both models. The cloud continues from the regenerated chunk, so the small model never builds a long history of its own, and no cache tensor is ever transmitted.

Robustness

Responding without the network

The device model regenerates where the action arrives, so a new action does not wait for the cloud, and the same path covers cloud chunks that are late or missing. With every message held for 2 to 20 s once per clip, the video of HIVE pauses for about 0.3 s per clip, while a device that can only decode waits for the cloud.

Player stall during a network outage
20-scene set, real-time runtime with a 16-FPS player, outage 10 s into each clip, 80 inputs per point. With 20 s the cloud does not return before the clip ends. During an outage the device generates the chunks itself, 13 to 26 of the 39 per clip, so these chunks have the quality of the device model; their videos are not scored.

Design space

Where to spend the cloud

More cloud steps per chunk change the judged quality little but push the throughput below the playback rate. Giving the device more chunks lowers the cloud cost but costs quality or camera accuracy. Which chunks the device generates matters more than how many.

Scope

Limitations

  • One-step chunks are softer than four-step chunks, so the imaging quality of HIVE stays below that of the cloud model (65.3 against 66.4 MUSIQ).
  • Device regeneration needs a device that runs the small model at the playback rate, here a workstation GPU (RTX PRO 6000). An RTX A5000 does not, and leaves regeneration to the cloud.
  • The device model does not raise the judged quality. Its contribution is the response to a new action and the playback during network problems.
  • After an outage the device keeps generating until the cloud leads again, 16 of the 39 chunks of a clip on average, at the quality of the device model.
  • With an action change every 3 s the quality falls significantly below the four-step cloud model.
  • Actions are scripted, the visual scores come from automatic metrics and a VLM judge, and the cost is measured with both GPUs in one host, an injected network delay, and one cloud GPU per user. A human study, closed-loop play, and a wide-area deployment are future work.
